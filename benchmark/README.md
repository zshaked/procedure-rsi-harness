# Benchmark: outcome-only procedure induction under a budgeted oracle

Working name: **τ-mail** (placeholder). Two sources: an inversion of τ-bench's airline and retail domains, and one synthetic operations domain built from scratch. Both produce the same artifact: a time-ordered history of `(request, state, response)` triples generated by a hidden policy, plus a budgeted noisy oracle.

Status: nothing generated yet. Build order is §9. The kill test (`../paper/OUTLINE.md` §9) runs on the synthetic domain first because it is the one we fully control.

---

## 1. What a domain consists of

| Component | Hidden from methods? | Notes |
|---|---|---|
| Policy document `Π` | **Yes** | The written procedure. The gold agent reads it; methods never do. Grading uses it. |
| State `s` (database) | No (replayable snapshot per case) | Methods call tools against the snapshot. |
| Tools `T` | No | Closed vocabulary; same tools for gold agent and methods. |
| Request generator | No | Templates over the database; completeness is a knob. |
| Gold agent | **Yes** | Policy-following agent (frontier model + `Π` + tools). Produces responses and action traces. |
| Oracle `O` | Query-only, budgeted | Judge with `Π` visible, noise `ρ`, cost per query. Answers yes/no + one-sentence reason citing the rule. |
| Hidden anchor `O*` | **Yes** | Same as `O` with `ρ = 0`, unlimited, used only for grading. |

## 2. Synthetic operations domain ("confirmations")

Built from scratch so it is publishable, generic, and fully controlled.

**State.** Accounts, instruments, positions (settled quantity, pending quantity, expected settlement date), instructions, contacts with authorization levels. ~2k accounts, ~500 instruments, ~20k positions. Generated with fixed seeds.

**Tools.** `lookup_account(query)`, `get_positions(account, instrument?, as_of)`, `get_pending(account, instrument)`, `get_contact(email)`, `get_instruction(id)`. Each returns JSON from the snapshot. Deterministic.

**Policy `Π` (v1), ~20 rules, examples:**
- Confirm only to contacts with authorization level ≥ 2; otherwise request authorization.
- The as-of date is the date stated in the request body; if none, use the request date and say so.
- Report settled and pending separately; if pending > 0, state the expected settlement date.
- If the account cannot be uniquely resolved, request clarification; never guess.
- If the instrument is not held, say so explicitly rather than reporting zero.
- Escalate if the requested quantity differs from the held quantity by more than 10%.
- …

**Policy `Π` (v2), for drift:** change 3 rules (e.g. authorization threshold ≥ 3; pending reported only if > 100 units; escalation threshold 5%).

**Requests.** Templated emails over sampled `(contact, account, instrument, as_of)` with knobs: completeness (all / missing as-of / ambiguous account / missing instrument), tone variation, distractor text. ~40 templates × paraphrase.

**Outcome classes.** `confirmed`, `not_held`, `request_info`, `request_authorization`, `escalate`.

**Complexity buckets.** Entities to resolve (1–3) × hops (1–3) × completeness (complete / partial / ambiguous).

## 3. τ-mail: inverting τ-bench airline and retail

τ-bench provides a policy document, a database, tools, and multi-turn tasks with a simulated user. Convert to single-shot:

1. **Single-turn requests.** Sample scenarios from the database (users, orders, reservations); render as one email containing all facts the gold agent needs — or, for the completeness knob, deliberately omit one.
2. **Gold agent** answers in one message. Outcomes map to τ-bench's end-state actions plus a `request_info` class when the request is incomplete.
3. **Record** `(request, snapshot_before, response, snapshot_after, actions)`; hide `actions` and `Π`.
4. Keep τ-bench's end-state check as a grader where actions exist; use `O*` for response adequacy.

Expected yield: ~500 cases per domain from τ-bench's databases without new content.

## 4. Knobs

| Knob | Values | What it tests |
|---|---|---|
| History size `N_H` | {0, 50, 400} | κ₀ and the exchange rate |
| Operator inconsistency `ρ_op` | {0, 0.1, 0.3} | Noise floor; split: harmless (valid rephrasing) vs harmful (one rule violated) at ratio 2:1 |
| Drift | off / `Π` v1 → v2 at index 0.6·N | Non-stationarity; post-drift split |
| Oracle noise `ρ` | {0, 0.1} | Verdict reliability |
| Oracle budget `B` | {0, 10, 25, 50, 100, 200} total; or per-epoch | Label efficiency |
| Completeness mix | complete / partial / ambiguous ∈ {0.6, 0.25, 0.15} | Escalation behavior |
| Representation | graph / skill / script | H5 |

---

## 5. Splits

Time-ordered. `dev` = oldest 60%; `sealed` = next 25%; `post_drift` = last 15% (generated under `Π` v2 when drift is on). A `rolling` split is simulated by generating fresh cases on demand under the current policy.

Methods see `dev` histories and may query the oracle about any case. `sealed` and `post_drift` are graded by `O*` only.

---

## 6. Oracle simulator

```
query(case_id, candidate_response) -> {verdict: 0|1, reason: str}
```

- Computes `acc` against `Π` with `O*`; flips with probability `ρ`.
- `reason` names the violated rule (or "acceptable"), lightly paraphrased so methods cannot string-match rules.
- Charges `c_V` per query; `c_R` for a rule-confirmation query (`confirm_rule(text) -> 0|1`), available only in the `rules` channel condition.
- Logs every query; the budget is enforced by the harness, not trusted to the method.

## 8. Evaluation

| Metric | Source | Reported on |
|---|---|---|
| Pass rate (floor) | deterministic checks vs snapshot + response facts | sealed, post_drift, per bucket |
| Adequacy | `O*` verdict on the method's response | sealed, post_drift |
| End-state match | τ-bench grader where actions exist | τ-mail domains |
| κ, Brier, Goodhart gap | verifier vs `O*` on a random slice | per epoch |
| Coverage at risk | conformal threshold on the random slice | per bucket |
| Oracle cost | logged queries × cost | cumulative |
| Structuredness | `../paper/MATH.md` §4.2 | per epoch (H5) |

Budget estimate (synthetic domain, one config, one seed): 400 cases × k=8 × ~5 epochs ≈ 16k rollouts + ~6k judge calls; gate ≈ 150 × 4 × 2 per epoch. Kill test: one long-context call per split plus ~200 ReAct executions.

## 9. Build order

1. **Synthetic domain generator** — state, tools, `Π` v1/v2, request templates. Deterministic from seed.
2. **Gold agent + history generation** — produce `N_H = 400` with `ρ_op = 0.2`, drift on. Verify with `O*` that unperturbed gold responses score `acc = 1` (≥ 98%; the rest are gold-agent errors, which are kept and logged — real operators err too).
3. **Oracle simulator + budget accounting.**
4. **Kill test** (`../paper/OUTLINE.md` §9): long-context baseline on `sealed` and `post_drift`.
5. **Floor checks** for the domain (entity, figure, as-of date, outcome class).
6. **τ-mail conversion** for airline, then retail.
7. **Harness adapter**: the design in `../DESIGN.md` running against this benchmark instead of a firm engine (the engine is any LangGraph executor of the chosen representation).
8. Baselines in `../paper/OUTLINE.md` §6.

Steps 1–4 are the first weekend. If step 4 passes the kill threshold, stop and reassess before step 5.

---

## 10. What this benchmark is not

- Not a measure of model capability: all methods use the same policy model.
- Not multi-turn: single-shot requests by design, so that histories are outcome-only.
- Not a substitute for real operators: `ρ_op` and `ρ` are stand-ins for human inconsistency, and the paper says so. The real-desk run (`../paper/OUTLINE.md` X8) is the external-validity check.
