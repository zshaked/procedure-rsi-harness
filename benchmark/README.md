# Benchmark: outcome-only procedure induction under a budgeted oracle

Working name: **τ-mail** (placeholder). Two sources: an inversion of τ-bench's airline and retail domains, and one synthetic operations domain built from scratch. Both produce the same artifact: a time-ordered history of `(request, state, response)` triples generated by a hidden policy, plus a budgeted noisy oracle.

Status: nothing generated yet. Build order is §9. The two-week pilot (`../paper/OUTLINE.md` §9) runs on the synthetic domain first because it is the one we fully control.

**v0.2 corrections (after external review).** (1) Hidden policies are **executable predicates**, not an LLM with the policy document: correctness is computed, so verifier exploitation is measured against ground truth independent of any model's opinion. (2) Each domain has **multiple policy instances**, and some are **held out**: methods are tested on specifications they never saw, not only on emails they never saw. (3) The LLM "oracle" is only a noisy *query channel*; it never grades.

---

## 1. What a domain consists of

| Component | Hidden from methods? | Notes |
|---|---|---|
| Policy `Π` — **executable** | **Yes** | A set of predicates `rule_j(request, state, response) → {satisfied, violated, n/a}` plus a decision function giving the required outcome class. Written in code. Also rendered to a policy document for the gold agent. Multiple instances per domain (`Π^(1)…Π^(m)`), some held out. |
| State `s` (database) | No (replayable snapshot per case) | Methods call tools against the snapshot. |
| Tools `T` | No | Closed vocabulary; same tools for gold agent and methods. |
| Request generator | No | Templates over the database; completeness is a knob. |
| Gold agent | **Yes** | Policy-following agent (frontier model + rendered `Π` + tools). Produces responses and action traces. Its responses are checked against the executable `Π`; failures are kept as gold-agent errors and logged (real operators err too). |
| Oracle `O` | Query-only, budgeted | LLM with rendered `Π` visible, noise `ρ`, cost per query. Answers yes/no + one-sentence reason citing the rule. **A noisy channel for methods; never a grader.** |
| Grader | **Yes** | The executable `Π`. Correctness of any response is computed. |

## 2. Synthetic operations domain ("confirmations")

Built from scratch so it is publishable, generic, and fully controlled.

**State.** Accounts, instruments, positions (settled quantity, pending quantity, expected settlement date), instructions, contacts with authorization levels. ~2k accounts, ~500 instruments, ~20k positions. Generated with fixed seeds.

**Tools.** `lookup_account(query)`, `get_positions(account, instrument?, as_of)`, `get_pending(account, instrument)`, `get_contact(email)`, `get_instruction(id)`. Each returns JSON from the snapshot. Deterministic.

**Policy `Π` (v1), ~20 rules, examples:**
- Confirm only to contacts with authorization level ≥ 2; otherwise request authorization.
- The as-of date is the date stated in the request body; if none, use the request date and say so.
- Report settled and pending separately; if pending > 0, state the expected settlement date.
- If the account cannot be uniquely resolved, request clarification; never guess.
- If the instrument is not held, say so explicitly rather than reporting zero.
- Escalate if the requested quantity differs from the held quantity by more than 10%.
- …

**Policy instances.** Generate `m ≥ 5` instances per domain by sampling rule parameters (authorization threshold, pending-reporting threshold, escalation tolerance, as-of default) and including/excluding optional rules from a pool of ~30. Instances are implemented as executable predicates and rendered to text for the gold agent and oracle. **Hold out ≥ 2 instances** for final test: a method that only works on specifications it saw is not inducing procedures, it is memorizing one.

**Drift (deferred):** an instance switch at index 0.6·N remains available as a knob but is not used in the pilot or X1–X7.

**Requests.** Templated emails over sampled `(contact, account, instrument, as_of)` with knobs: completeness (all / missing as-of / ambiguous account / missing instrument), tone variation, distractor text. ~40 templates × paraphrase.

**Outcome classes.** `confirmed`, `not_held`, `request_info`, `request_authorization`, `escalate`.

**Complexity buckets.** Entities to resolve (1–3) × hops (1–3) × completeness (complete / partial / ambiguous).

## 3. τ-mail: inverting τ-bench airline and retail

τ-bench provides a policy document, a database, tools, and multi-turn tasks with a simulated user. Convert to single-shot:

1. **Single-turn requests.** Sample scenarios from the database (users, orders, reservations); render as one email containing all facts the gold agent needs — or, for the completeness knob, deliberately omit one.
2. **Gold agent** answers in one message. Outcomes map to τ-bench's end-state actions plus a `request_info` class when the request is incomplete.
3. **Record** `(request, snapshot_before, response, snapshot_after, actions)`; hide `actions` and `Π`.
4. Keep τ-bench's end-state check as a grader where actions exist. Response adequacy in τ-mail has no executable grader unless the τ-bench policy is re-implemented as predicates (a real cost, scheduled after the pilot); until then τ-mail reports end-state match only, and the synthetic domain carries all adequacy claims.

Expected yield: ~500 cases per domain from τ-bench's databases without new content.

## 4. Knobs

| Knob | Values | What it tests |
|---|---|---|
| History size `N_H` | {0, 50, 400} | κ₀ and the exchange rate |
| Operator inconsistency `ρ_op` | {0, 0.1, 0.3} | Noise floor; split: harmless (valid rephrasing) vs harmful (one rule violated) at ratio 2:1 |
| Drift | off / `Π` v1 → v2 at index 0.6·N | Non-stationarity; post-drift split |
| Oracle noise `ρ` | {0, 0.1} | Verdict reliability |
| Oracle budget `B` | {0, 10, 25, 50, 100, 200} total; or per-epoch | Label efficiency |
| Completeness mix | complete / partial / ambiguous ∈ {0.6, 0.25, 0.15} | Escalation behavior |
| Representation | graph / skill / script | H5 |

## 5. Splits

Four roles, matching `../DESIGN.md` §7, plus a policy-level holdout:

| Role | Cases | Policy instances |
|---|---|---|
| Learning | oldest 50% of each seen instance's history | seen instances only |
| Search validation | next 25% | seen instances |
| Calibration | fresh requests, responses from the *current* policy, oracle-labeled from the calibration budget | seen instances |
| Final test | newest 25% **and** the full history of held-out instances | seen + **held-out** |

Methods see learning histories and may spend their expert-seconds budget on oracle queries about learning or calibration cases. Everything is graded by the executable `Π`; nothing is graded by an LLM.

## 6. Oracle simulator

```
query(case_id, candidate_response) -> {verdict: 0|1, reason: str}
```

- Computes `acc` with the executable `Π`, then flips the verdict with probability `ρ`, so the oracle's noise is exactly `ρ` and nothing else.
- `reason` names the violated rule (or "acceptable"), lightly paraphrased so methods cannot string-match rules.
- Charges `c_V` per query; `c_R` for a rule-confirmation query (`confirm_rule(text) -> 0|1`), available only in the `rules` channel condition.
- Logs every query; the budget is enforced by the harness, not trusted to the method.

## 8. Evaluation

| Metric | Source | Reported on |
|---|---|---|
| **Correctness** | executable `Π`: all applicable rules satisfied and required outcome class produced | final test (held-out cases **and** held-out policy instances), per bucket; **reference-free** |
| Pass rate (floor) | deterministic fact checks vs snapshot | search validation, per bucket |
| End-state match | τ-bench grader where actions exist | τ-mail domains |
| Verifier error map | verifier verdict vs executable `Π`, per rule and bucket, on the current policy's outputs | before and after optimization (H3) |
| κ, Brier, exploitation gap | verifier vs executable `Π` on the random-calibration slice | per epoch |
| Coverage at bounded risk | selective-risk procedure (`../paper/MATH.md` §3) | marginal; per bucket where budget allows |
| Expert seconds | logged queries × seconds per query type (`c_V`, `c_R` in seconds) | cumulative; the budget axis |
| Oracle cost | logged queries | cumulative |

Expert time is the budget unit. Rule confirmation and response verdicts cost different seconds; the benchmark fixes those costs (defaults: rule confirmation 15 s, verdict with reason 60 s) and reports everything against seconds, so arms that ask different kinds of questions are comparable.

Budget estimate (synthetic domain, one config, one seed): 400 cases × k=8 × ~5 epochs ≈ 16k rollouts + ~6k judge calls; gate ≈ 150 × 4 × 2 per epoch. Kill test: one long-context call per split plus ~200 ReAct executions.

## 9. Build order (two-week pilot first)

1. **Synthetic domain generator** — state, tools, request templates, and `m = 5` **executable** policy instances (2 held out). Deterministic from seed.
2. **Gold agent + history generation** — per instance, `N_H = 400` with `ρ_op = 0.2`. Check gold responses against the executable `Π`; keep and log failures as gold-agent errors.
3. **Oracle simulator + expert-seconds accounting.**
4. **True-spec-revealed** run: the agent given the rendered `Π`. Execution ceiling.
5. **Floor checks** (entity, figure, internal consistency — not outcome class).
6. **Pilot arms** (`../paper/OUTLINE.md` §9): long-context induction, retrieval few-shot, spec-once-then-policy, policy-first, verifier-first — matched on histories, expert answers, expert seconds, compute. Verifier-first at reduced `k` and epochs.
7. **Evaluate fresh outputs reference-free against executable `Π`**, including on the 2 held-out instances. Verifier error map before/after optimization.
8. Decide per `../paper/OUTLINE.md` §9. Only then: τ-mail conversion, full harness adapter, remaining baselines.

Steps 1–4 are the first week; 5–8 the second.

---

## 10. What this benchmark is not

- Not a measure of model capability: all methods use the same policy model.
- Not multi-turn: single-shot requests by design, so that histories are outcome-only.
- Not a substitute for real operators: `ρ_op` and `ρ` are stand-ins for human inconsistency, and the paper says so. The real-desk run (`../paper/OUTLINE.md` X8) is the external-validity check.
